# Build system

The firmware is built with **CMake + Ninja** on Windows. The SDK itself uses SCons; this project reproduces the
SDK's compile commands in CMake so that the build is fast, scriptable and independent of the SDK's application
directory structure.

## Requirements

* Windows 10 / 11, Git, Python 3.9+ (only to create the helper venv), CMake 3.20+.
* A project path **without spaces**.
* Network access for the first `setup.ps1` (fetches the one pinned SDK commit without history, about 0.5 GB, 3.3 GB on disk with the toolchain).

The SDK brings its own RISC-V toolchain (`riscv64-unknown-elf-gcc`, T-Head, with the `xtheade` extensions), Python 2.7
and 3.9, SCons and the packaging tools (`mkimage`, `mk_image.exe`). Nothing else is installed system wide; Ninja and
PyInstaller live in `.local\venv`.

## Quick start

```powershell
powershell -File scripts\setup.ps1          # once: clone the SDK, overlay the board, apply the defconfig, install Ninja
powershell -File scripts\build.ps1          # configure + build; images in build\images\
powershell -File scripts\build.ps1 -Clean   # from scratch
powershell -File scripts\build.ps1 -UsbDebug   # also log every USB control request on the UART
powershell -File scripts\build.ps1 -AppLog 2   # verbose application log: every command, status line every 5 s
```

CMake cache options (set with `-D...` or through the `build.ps1` switches `-AppLog` / `-UsbDebug`): `AKP05_APP_LOG` (0 errors only, 1 events (default), 2 verbose),
`AKP05_USB_DEBUG` (ON/OFF), `AKP05_DEFCONFIG`, `SDK_DIR`.

The firmware version is the plain variable `AKP05_FW_VERSION` at the top of `CMakeLists.txt` ("settings you may want to
change"); edit it there. The log level, the USB debug switch and the defconfig are cache entries next to it.

**Boot screen banner.** Until a host connects, the screen shows the logo with a black strip at the bottom that reads
`AKP05E OPEN FIRMWARE <version>-<git hash>` and `BUILT <date> <time>` (without a logo file the screen is black with just
the strip). The time is that of the CMake configure step, which `build.ps1` runs on every build; only `display.c` is
recompiled for it. The text is drawn by the CPU with a 5x7 font (`firmware/app/font5x7.h`, generated by
`scripts/maintenance/gen_font5x7.py`, upper case, digits and `. - : / _ ( ) +` only); the first host command that clears
the screen removes it. The panel is mounted upside down relative to the frame buffer, so the banner is drawn rotated by
180 degrees in buffer coordinates (`BANNER_ROTATE_180` in `display.c`, set it to 0 for a panel that is not rotated).

## Preflight checks

`build.ps1` refuses to run unless `setup.ps1` was done (SDK, toolchain, generated headers, Ninja present, and the board /
defconfig / image config in `sdk\` identical to `firmware\`); `make_test_kit.ps1` refuses to run unless `build.ps1` produced
all four components (and `d13x_os.itb` is a FIT), and warns when `firmware\` is newer than the last build;
`build_host_tool.ps1` needs only Python. Each failure names the script to run first (`scripts/lib/checks.ps1`).

## The scripts leave your session alone

`setup.ps1`, `build.ps1`, `build_host_tool.ps1`, `make_test_kit.ps1` and `maintenance/refresh_sdk_sources.ps1` save the working
directory and `PATH`, `PYTHONPATH`, `ENV_ROOT`, `PKGS_ROOT` when they start and restore them in a `finally` block
(`scripts/lib/session.ps1`), also after an error. Run them as `.\scripts\build.ps1` from any directory and you stay where you were.

## What `setup.ps1` does

1. `git clone` of `https://github.com/artinchip/luban-lite.git` into `sdk/` (or the path given with `-SdkSource`) and
   `git checkout 77fbe30d...` (Luban-Lite **v1.0.3**, the version the stock firmware is based on).
2. **Overlay** into the SDK tree: `firmware/board/akp05-nor/*` -> `sdk/target/d13x/akp05-nor`,
   `firmware/image/{image_cfg.json,env.txt}` -> `.../pack`, `firmware/config/<defconfig>` -> `sdk/target/configs`.
3. Creates `.local/venv` with Ninja.
4. `scons --apply-def=<defconfig>` (SDK Python 2.7): writes `.config`, `rtconfig.h` and unpacks the SDK toolchain;
   `scons -n` (dry run, nothing is compiled) generates `cconfig.h`, `partition_table.h` and the linker script.

## What `CMakeLists.txt` does

* Selects the toolchain (`cmake/toolchain-riscv-xtheade.cmake`).
* Runs the Kconfig step once if `sdk/rtconfig.h` is missing.
* Generates `partition_table.h` / `partition_file_list.h` from **our** `firmware/image/image_cfg.json` (so the
  partition layout has a single source of truth) and puts them first on the include path.
* Includes `cmake/sdk_sources.cmake` (the SDK's flags, defines, include directories and **source list in the
  SCons link order**, plus per-file extra include directories) and `firmware/app/sources.cmake` (the application).
* Copies the SDK linker script to `build/akp05.ld`, replacing `startup_gcc.o(` by `startup_gcc.S.obj(`: the script
  places the startup code first by object name, and CMake names objects `*.obj`. This is what puts the entry point at
  `0x40210000`.
* Links with `-Wl,--start-group -lm -lc -lgcc -Wl,--end-group` after the objects (SCons links with `g++`, whose driver
  appends the libraries; with `gcc` they must be explicit, otherwise `sin` / `cos` are undefined).
* Post build: `akp05_fw.elf` / `.bin`, then the `image` target runs `scripts/pack_image.py`
  (see [architecture.md](architecture.md#4-from-elf-to-flash-image)).

## The SDK source list is generated

`cmake/sdk_sources.cmake` is generated and **committed** (CI needs it) from a full verbose SCons build:

```powershell
powershell -File scripts\maintenance\refresh_sdk_sources.ps1     # several minutes
```

**Run it after every change of `firmware/config/*_defconfig`**: the defconfig decides which SDK files are compiled
(for example, switching LVGL off removed 196 of 403 source files). The script runs `scons --verbose`, tolerates the
expected final failure of `mk_image` (no vendor updater in `image_cfg.json`), checks that everything compiled and
linked, and runs `scripts/maintenance/gen_sdk_cmake.py` to rewrite the CMake file. Then build and test.

## Rules for the defconfig (`firmware/config/d13x_akp05-nor_rt-thread_akp05fw_defconfig`)

The file started as the vendor's `helloworld` defconfig. It is applied with `scons --apply-def`, which **does not
re-evaluate Kconfig defaults**: every option a driver needs must be listed explicitly, derived ones included.
Examples: `CONFIG_AIC_PWM_DRV=y` alone is not enough, the file also needs `CONFIG_AIC_PWM_DRV_V10=y`,
`CONFIG_AIC_PWM_DRV_VER="10"` and `CONFIG_AIC_PWM_CH_NUM=4`, otherwise `drv_pwm.c` fails to compile.

Settings that matter for this device (do not change them without a reason):

| Option | Value | Why |
|---|---|---|
| `CONFIG_AIC_PSRAM_SW_SIZE` | `0x210000` | puts the load address at `0x40210000`, like the stock image |
| `CONFIG_AIC_DI_TYPE` | `1` | RGB display interface (the vendor value `2` is LVDS and breaks `aicfb_probe`) |
| `CONFIG_AIC_PWM_DRV*` | see above | backlight |
| `CONFIG_LPKG_CHERRYUSB_DEVICE_AIC_CPU` | `y` (DMA off) | the DMA mode breaks EP0 data stages (see troubleshooting.md) |
| `CONFIG_LPKG_USING_LVGL` | not set | the vendor demo draws over the display; the stock firmware has no LVGL |
| `CONFIG_FINSH_PROMPT_NAME` | `"arx"` | prompt of the stock firmware |
| `CONFIG_AIC_USB_DEVICE_DRV`, CherryUSB device HID, I2C2 | `y` | explicit, `select` chains do not apply |
| `CONFIG_PRJ_DEFCONFIG_FILENAME` | this file's name | otherwise the SDK re-applies the helloworld config |

## Build outputs and where they go

| Path | Content | Created by |
|---|---|---|
| `build/` | CMake tree, `build/images/*` firmware, `build/logs/` | `build.ps1` |
| `dist/akp05_tool.exe` | the host tool | `build_host_tool.ps1` |
| `dist/akp05_test_kit/` and `.zip` | tool + firmware + launchers + backup | `make_test_kit.ps1` |
| `sdk/`, `.local/` | SDK clone, helper venv | `setup.ps1` |

All of them are ignored by git and safe to delete: the scripts recreate them.
`powershell -File scripts\clean.ps1` removes `build\`, `dist\` and the Python caches; with `-All` it also removes `sdk\` and `.local\`
(use it before you copy or archive the project; `private\` and tracked files are never touched).

## Where the SDK comes from (download and reuse)

* **Locally the SDK is fetched once.** `setup.ps1` fetches only the pinned commit (no history) into `sdk\`, about 0.5 GB,
  1 - 2 minutes. `sdk\` stays after `build.ps1 -Clean` and `clean.ps1`; only `clean.ps1 -All` removes it, and then the
  next `setup.ps1` fetches it again.
* **No network for a second copy:** keep one clone of Luban-Lite on the machine and point the setup at it:
  `setup.ps1 -SdkSource C:\path	o\luban-lite`. The pinned commit is fetched from that path.
* **GitHub Actions cache `sdk\`** (`actions/cache`, key from the board / config files), so a run restores it instead of
  fetching. GitHub restores caches that were saved on the same branch or on the default branch: the `ci` workflow
  saves it on every push to `main`, the `release` workflow (tag runs) restores that one. The first run, and a run after
  the cache was evicted (unused for 7 days), fetches the SDK again.

## Continuous integration

`.github/workflows/ci.yml` (windows-latest): unit tests of the host tool; the host tool `.exe` (artifact `akp05-tool`);
the firmware (cache of `sdk/`, `setup.ps1`, `build.ps1`, SHA-256 sums, artifact `akp05-firmware`). It runs on pushes to
`main` and on pull requests.

`.github/workflows/release.yml` runs when a tag `v*` is pushed: it checks that the tag is `v` + `AKP05_FW_VERSION`, builds the
firmware, the tool and the test kit (without backup and vendor updater) and creates the release with all of them; see
[releasing.md](releasing.md). Neither workflow has been run on GitHub yet (they follow the same steps that work locally).

## Reproducibility

A clean checkout builds a functionally identical `d13x_os.itb`; it is not bit-identical because the build date and the
absolute source paths are embedded in the binary.
